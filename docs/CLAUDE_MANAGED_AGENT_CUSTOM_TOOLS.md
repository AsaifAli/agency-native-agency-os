# Claude Managed Agents — OS Custom Tool Bridge

## Security boundary

The Managed Agents runtime now accepts only custom tool definitions generated by the Agency OS Tool Registry. It rejects built-in toolsets, MCP servers, skills, multiagent features, unknown custom tools and any schema/description drift.

Custom tool calls are not trusted because they originated from the provider. The provider emits an `agent.custom_tool_use` event; the worker sends the input to the in-process OS Tool Gateway. The gateway verifies the agent's machine identity, active session, organization/workspace scope, data class, exact tool grant and idempotency before executing. The worker then returns a `user.custom_tool_result` event. Raw exceptions, provider secrets and untrusted payloads are never copied into the provider response.

The provider's custom-tool permission policies are not the authorization boundary. OS authorization is enforced in backend code for every invocation.

## Registered custom tools

The runtime currently exposes only:

| Provider tool name | OS tool key | Purpose |
|---|---|---|
| `os_system_health_read` | `system.health.read` | Minimal API/database health |
| `os_revenue_lead_research_capture` | `revenue.lead.research.capture` | Capture public company research as a founder-review draft |

Generate the exact current definitions from the source of truth:

```bash
python - <<'PY'
import json
from app.tool_registry import managed_agent_custom_tool_definitions
print(json.dumps(managed_agent_custom_tool_definitions(), indent=2))
PY
```

Configure the provider Agent with those exact `type=custom`, `name`, `description` and `input_schema` values. The adapter rejects schema drift. Do not add provider built-in tools, MCP servers, skills or multiagent configuration. Web search/fetch is not enabled in this bridge; public-source discovery still requires a separately reviewed, DPG-aware search adapter.

## Machine identity required for business tools

For an Agent with ID `{agent_id}`, issue a founder-governed machine identity in the same organization and workspace:

- `subject_type=agent`
- `subject_id={agent_id}`
- scopes: `sessions:create`, `tools:invoke`, `tool:revenue.lead.research.capture`
- allowed data classes: `public` only
- bounded expiry and revocation policy

The worker lazily creates/reuses a durable `AgentSession` when the provider emits a custom tool event. Its ID is stored on the scoped `Execution.machine_session_id` column through a composite org/workspace/session foreign key. A session is never shared across executions or workspaces. Session creation audit is emitted by the shared lifecycle service for both HTTP and worker paths.

If the identity is missing, expired, revoked, lacks session permission, or lacks the exact tool grant, the OS returns a generic tool-denied result. It does not fall back to provider permissions.

## Reliability

- Provider custom-tool event IDs are deterministically hashed into OS idempotency keys.
- Tool invocation and business draft persist before the provider receives the result event. Denied calls roll back uncommitted adapter work and persist a safe reason-code audit event.
- If the worker restarts after the OS commit but before returning the event, the same event ID replays the stored result rather than creating another draft.
- The adapter checks event history while sessions are running, not only after idle.
- It waits for the provider to resume after a custom-tool result, but does not auto-confirm built-in tool actions.
- Machine sessions are expired by the bounded worker maintenance loop and each lifecycle transition is audited.

## Data and approval rules

- The Revenue research capture tool accepts public data only, rejects contact fields and arbitrary extra properties, applies DPG and creates a pending-review draft.
- Founder Authority must approve the draft and separately promote it to CRM.
- No tool sends outreach, creates contacts, changes consent, commits pricing, signs contracts or initiates payments.
- Tools marked as requiring approval remain blocked until a transactional approval adapter is implemented.
- No provider web search, web fetch, shell, filesystem, browser or MCP tool is enabled by this bridge.

## External configuration still required

1. Set `ANTHROPIC_API_KEY` and `CLAUDE_MANAGED_AGENT_ID` only in the server-side secret manager.
2. Configure the provider Agent's custom tool definitions from the generator above.
3. Issue the machine identity for the corresponding OS Agent using Founder Authority.
4. Keep the runtime on public/synthetic data until data eligibility is explicitly verified.
5. Run the synthetic end-to-end tool test and PostgreSQL 16 migration verification before production use.

Claude Managed Agents is beta and not eligible for ZDR or HIPAA BAA. Do not route confidential or regulated client data through this runtime. This adapter is not a compliance claim.


## API contract reference

The adapter follows the Managed Agents custom-tool event contract: the provider emits `agent.custom_tool_use`; the application executes the tool; the application sends a `user.custom_tool_result` event with the original `custom_tool_use_id` and text content. The worker watches event history while the session is running and waits for the provider to resume after the result. It never sends `user.tool_confirmation` for built-in actions.
